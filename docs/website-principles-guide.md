# 网站搭建与部署：从零讲透每一步的原理

> 本文面向「跟着做完了但还不完全理解」的读者，用通俗语言 + 类比，把网站从代码到上线的每一步「是什么、为什么、有什么用」讲清楚。以本项目（GTA6 情报站，多语言）为实例。

---

## 第一部分：网站到底是什么

### 1. 一个网站的本质

网站本质上是一堆**放在服务器上的文件**。当你用浏览器打开一个网址时：

1. 浏览器向服务器发起请求（"把首页给我"）
2. 服务器把文件（HTML）传回来
3. 浏览器把 HTML 渲染成你看到的页面

其中 **HTML** 是页面的"骨架和内容"，**CSS** 是"样式"（颜色、布局），**JS** 是"行为"（点击、倒计时、语言切换）。

### 2. 静态网站 vs 动态网站

- **静态网站**：服务器上就存着现成的 HTML 文件，谁来访问都返回同一个文件。快、便宜、稳。
- **动态网站**：服务器收到请求后，现场"算"出一个 HTML（比如根据你的登录状态、数据库数据拼出来）。灵活，但需要一直运行的服务器。

**本项目选的是静态**：GTA6 的情报/攻略是发布时就定好的内容，没有登录、没有用户数据，所以完全可以预先生成好所有 HTML，谁访问直接给。

### 3. 类比

- 静态网站 = 一家把菜**提前做好**摆在柜台的餐厅（客人来了直接端，快）
- 动态网站 = 一家**现点现做**的餐厅（每个客人都要现炒，慢但能定制）

## 第二部分：我们用的"工具链"是什么

### 1. Node.js（运行环境）

让 JavaScript 能在**服务器/电脑上**运行（而不是只能在浏览器里）。所有"构建"命令（`npm run build`）都是在 Node.js 里跑的。

### 2. React（界面库）

把界面拆成**一个个可复用的"组件"**（比如 Header、Footer、卡片），像搭积木一样组页面。管理状态、自动更新界面。

### 3. Next.js（框架）

在 React 基础上加了**路由**（URL 对应哪个页面）、**构建/优化**（把源码编译成高效文件）、**SEO 支持**等一整套能力。我们用它是因为它能"一键生成静态网站"。

### 4. TypeScript（语言）

JavaScript 的"加类型"版本：写代码时就能发现错误（比如把字符串传给了要数字的地方），减少 bug。

### 5. npm（包管理器）

管理项目依赖的第三方库（比如 gray-matter、react-markdown）。`package.json` 记录了"这个项目用了哪些库、怎么构建"。

**一句话串起来**：用 TypeScript 写 React 组件 → Next.js 负责路由和构建 → Node.js 跑构建 → npm 管依赖。

## 第三部分：构建（Build）到底做了什么

### 什么是"构建"

你写的源码（`.tsx`、`.md`）**浏览器看不懂**，也不能直接上线。`npm run build` 就是一台"翻译+打包"机器：

1. 读取所有源码
2. 编译 TypeScript → JavaScript
3. 把 Markdown 文章解析成 HTML
4. 生成每种语言、每篇文章的**静态 HTML 文件**
5. 输出到 `out/` 文件夹

`out/` 文件夹里的东西，就是**可以直接放上服务器的成品**。

### 为什么选"静态导出"（`output: 'export'`）

Next.js 默认是"动态"（要服务器运行时生成页面）。我们在 `next.config.ts` 里写 `output: 'export'`，就是告诉它："把**所有**页面在构建时就生成好，别留任何需要服务器现算的东西。"

**好处**：
- **无服务器成本**：不需要租一台一直运行的服务器，静态文件放任何地方（甚至免费 CDN）都行
- **快**：全球 CDN 缓存，访问者从最近的节点拿文件
- **SEO 友好**：搜索引擎抓到的就是完整 HTML，不用等 JS 执行
- **稳**：没有服务器就没有"服务器挂了"的问题

## 第四部分：内容管线（为什么用 Markdown）

### Markdown 是什么

一种**纯文本的轻量标记语言**。你用简单的符号（`#` 标题、`-` 列表、`**加粗**`）写内容，程序把它渲染成漂亮的 HTML。比直接写 HTML 简单得多。

### frontmatter 是什么

每篇 Markdown 顶部 `---` 之间的 YAML 块，存的是**元数据**（标题、日期、分类、标签、封面），和正文分开。这样程序能快速读取"这篇文章叫什么、属于哪个分类"，而不需要解析整篇正文。

### 为什么用 Markdown + 文件，而不是数据库

| 方式 | 优点 | 缺点 |
|---|---|---|
| Markdown 文件 | 人写方便、git 版本管理、AI 易读、无需后端 | 内容多了要管理文件 |
| 数据库 | 动态增删改、适合海量 | 需要服务器、查询代码、迁移麻烦 |

**对内容站（文章为主的网站）来说，Markdown 文件是"发稿零代码"的最优解**：新增一篇文章 = 往 `content/` 丢一个 `.md` 文件，改几行 frontmatter，不用改任何代码。

### 代码怎么读到这些文件

`src/lib/content.ts` 用 `fs`（文件系统模块）读 `content/{语言}/{类型}/*.md`，用 `gray-matter` 解析 frontmatter，返回一个文章数组。页面拿到数组后渲染成列表和正文。

## 第五部分：多语言（i18n）的原理

### i18n 是什么

"国际化（internationalization）"的缩写——i18n 是因为这个词有 18 个字母（i...n 中间 18 个）。多语言网站要解决两件事：

1. **文案翻译**：界面上的"首页/情报/攻略"、文章正文，每种语言一套
2. **路由**：用户访问 `/en/...` 看到英文，访问 `/zh/...` 看到中文

### 为什么用"路径前缀"（/en/、/zh/）而不是 cookie

三种常见方案：

| 方案 | 原理 | 问题 |
|---|---|---|
| cookie/浏览器语言 | 记住用户上次选的语言 | 对 SEO 不友好（搜索引擎只看到一套页面） |
| 不同域名 | en.site.com / zh.site.com | 要买多个域名 |
| **路径前缀** | /en/... 和 /zh/... | **每个语言有独立 URL，可独立被搜索引擎收录** |

**路径前缀是 SEO 最优解**：每个语言版本都是一个独立、可被抓取、可配 hreflang 的 URL。

### 为什么路径前缀方案"被迫"用（不是可选）

关键点：我们的站是**静态导出**。而"根据访问者浏览器语言自动跳转"需要 middleware（运行时中间件）——静态导出**不支持**运行时能力。所以只能用路径前缀 + 用户手动切换语言。

### 字典系统原理

把所有 UI 文案放在一个"字典"对象里，每种语言一个字典文件（`translations/zh.ts`、`en.ts`…）。代码里不写死"首页"，而是写 `dict.navHome`——运行时根据当前语言取对应字典里的值。

**为什么要拆成 `locales.ts` 和 `i18n.ts` 两个文件**：这是一个很细但重要的坑。`i18n.ts` 里用了 `notFound()`（Next.js 的服务端函数）。而"语言切换器"是**客户端组件**（要在浏览器里运行）。如果客户端组件 import 了 `i18n.ts`，就会把服务端函数和四个字典全部打包进浏览器 JS（白白变大，甚至报错）。所以把**纯常量**（语言列表、类型）单独放 `locales.ts`，客户端只 import 它。

### 语言切换器原理

切换器是客户端组件，用 `usePathname()` 拿到当前 URL（比如 `/en/news/foo`），把开头的 `/en` 去掉得到 `/news/foo`，再对每个语言拼出 `/{新语言}/news/foo` 的链接。这样"切换语言"就保持在同一篇文章上。

## 第六部分：SEO（让搜索引擎找到你）

### 搜索引擎怎么工作

1. **爬虫**：搜索引擎的机器人不断访问网页，抓取内容
2. **索引**：把抓到的内容存进数据库
3. **排名**：用户搜索时，从索引里按相关性+质量排序返回

所以"做好 SEO"的本质 = **让爬虫方便地抓到你的内容，并告诉它内容的结构和语言关系**。

### 几个关键机制的作用

| 机制 | 是什么 | 作用 |
|---|---|---|
| **sitemap.xml** | 一个列出你所有网页 URL 的清单 | 主动告诉搜索引擎"我有这些页面，来抓" |
| **robots.txt** | 给爬虫的规则文件 | 告诉它"哪些能抓、sitemap 在哪" |
| **hreflang** | 在页面里标注"这个页面有哪些语言版本、对应 URL" | 避免被当成重复内容惩罚，正确引导各语言用户 |
| **JSON-LD** | 结构化数据（用 JSON 描述"这是一篇文章/作者/日期"） | 利于富结果展示，也利于被 AI 引用 |
| **`<html lang>`** | 告诉浏览器/爬虫这页是什么语言 | 无障碍 + 正确识别语言 |
| **canonical** | 声明"这个页面的标准 URL 是这个" | 避免重复内容 |

### 本项目怎么做的

每个页面的 `generateMetadata` 里返回 `alternates.languages`（hreflang 映射）。`sitemap.ts` 枚举 4 种语言 × 所有文章。`schema.ts` 生成 JSON-LD。**一个关键细节**：hreflang 只输出"该文章实际有译文"的语言，避免指向 404 的链接。

## 第七部分：域名与 DNS（为什么域名能指向你的站）

### 域名是什么

`gta6gameleaksandguides.asia` 是给人记的**名字**。但服务器实际靠 **IP 地址**（一串数字）找到。DNS 就是"名字 → IP"的翻译系统，相当于互联网的电话簿。

### 常见的 DNS 记录类型

| 记录 | 全称 | 作用 |
|---|---|---|
| **A** | Address | 域名 → IP 地址（"这个域名指向这台服务器"） |
| **CNAME** | Canonical Name | 域名 → 另一个域名（"这个域名是那个域名的别名"） |
| **NS** | Name Server | 指定"这个域名由哪家 DNS 服务器管理" |
| **TXT** | Text | 放任意文本（常用于**验证域名所有权**，比如 Google/Bing 让你加验证码） |

### 本项目为什么把 NS 从腾讯云迁到 Cloudflare

域名最初在腾讯云买、DNS 也归腾讯云管。但我们的站托管在 Cloudflare Pages。Cloudflare 有个"全家桶"优势：**DNS + CDN + HTTPS 证书 + Pages 托管**都在一个平台，配置互通、自动 HTTPS。

迁移 NS 后，域名的解析就交给 Cloudflare 了。之后 Cloudflare Pages 的"自定义域名"能自动接管路由（不用手动加 `@` CNAME），HTTPS 证书也自动签发。

### 为什么验证域名要加 TXT 记录

Google/Bing 要确认"你确实拥有这个域名"。它们让你加一条特定内容的 TXT 记录——**只有能改这个域名 DNS 的人**才能加。能加上，就证明你是主人。验证后这条记录可以留着（Google 建议保留，Bing 的可删）。

## 第八部分：托管与 CDN（Cloudflare Pages）

### 托管是什么

你的 `out/` 静态文件需要一个"家"——一台能让全世界访问的服务器。托管服务商提供这个。

### CDN 是什么

**内容分发网络**：把你的文件复制到全球各地的节点。访问者从**离他最近的节点**拿文件，而不是从唯一一台远在天边的服务器。所以快。

### Cloudflare Pages 的原理

1. 连上你的 GitHub 仓库
2. 你每次 `git push`，它自动触发：拉最新代码 → 跑 `npm run build` → 把 `out/` 部署到 CDN
3. 全程自动，你只管 push

### 为什么必须设 NODE_VERSION=22（踩过的坑）

这是本项目最经典的坑：Next.js 16 要求 Node.js **≥ 20.9**。但 Cloudflare Pages 默认用 **Node 18**（低于要求）。结果：**本地能构建成功（你本地 Node 24），线上却构建失败**（出现红叉）。

解法：在 Cloudflare 的环境变量里设 `NODE_VERSION=22`，让线上也用新版 Node。

**通用教训**：本地环境和线上环境不一致（Node 版本、依赖版本）是部署失败的常见原因。

## 第九部分：Git 版本控制

### Git 是什么

**版本控制系统**：记录文件的每次改动，能随时回退、查看历史、多人协作。

### commit / push 是什么

- **commit**：把当前改动"拍照存档"（存到本地，带一条说明）
- **push**：把本地存档上传到远程（GitHub）

**为什么每步都要 commit**：改动可追溯、可回退。而且本项目里 `push` 还会触发 Cloudflare 自动部署——所以 push 既是"存档"又是"发布"。

### 分支（branch）是什么

一条独立的开发线。可以在分支上做实验，不影响主分支（main），成熟后再合并。本项目最后把功能分支合并回 main，并删掉了冗余分支。

## 第十部分：完整链路回顾（一图流）

```
写代码 / 写 Markdown
        ↓
  npm run build（本地构建，把源码 + Markdown 编译成 out/ 静态文件）
        ↓
  git add + commit（存档改动）
        ↓
  git push origin main（上传到 GitHub）
        ↓
  Cloudflare Pages 自动检测到 push → 自动跑构建（用 NODE_VERSION=22）
        ↓
  把 out/ 部署到全球 CDN
        ↓
  用户访问 gta6gameleaksandguides.asia → DNS 解析到 Cloudflare → CDN 返回页面
```

**每一步的作用对照表**：

| 步骤 | 做了什么 | 原理/为什么 |
|---|---|---|
| 写 Markdown 内容 | `content/**/*.md` | 发稿零代码、git 可版本管理 |
| 静态导出配置 | `output:'export'` | 无服务器、CDN 快、SEO 好 |
| `[lang]` 路径前缀 | 每语言独立 URL | SEO 独立收录 + 可配 hreflang |
| 字典拆分 | locales.ts / i18n.ts | 客户端组件不能打包服务端代码 |
| hreflang 只输出存在译文 | seo.ts | 避免指向 404 的链接 |
| sitemap 枚举 4 语言 | sitemap.ts | 让搜索引擎发现全部语言版本 |
| JSON-LD | schema.ts | 富结果 + 利于 AI 引用 |
| NODE_VERSION=22 | Cloudflare 环境变量 | 满足 Next 16 的 Node 版本要求 |
| TXT/CNAME 记录 | 验证域名所有权 | 证明你是域名主人 |

## 第十一部分：踩坑清单（每个坑的"为什么"）

1. **`generateStaticParams` 的 params 不是 Promise**：页面组件的 `params` 是 `Promise`（要 `await`），但 `generateStaticParams` 收到的 `params` 是**同步普通对象**。因为生成静态参数发生在构建早期，参数是已知的，不需要异步等待。

2. **frontmatter 里的 ASCII 冒号 `: ` 破坏 YAML**：YAML 会把 `: `（冒号+空格）当成"键: 值"的分隔符。所以 `coverCaption: xxx · Source: Rockstar Games` 里的 `Source:` 被误判成新键，解析报错。中文原稿用全角 `：` 所以没事，英文翻译用了半角冒号就炸了。解法：加双引号。

3. **双 root layout 导致嵌套 `<html>`**：如果 `app/layout.tsx` 和 `app/[lang]/layout.tsx` 都写 `<html>/<body>`，后者会被嵌套进前者，产生非法的嵌套 HTML，且 `<html lang>` 永远是外层那个。解法：用路由组 `(root)` 把 `/` 的 layout 隔开，让 `[lang]` 的 layout 独立负责自己的 `<html lang>`。

4. **线上 Node 版本和本地不一致**：见第八部分，本地 Node 24、线上默认 18，导致"本地能建、线上失败"。解法：显式指定 `NODE_VERSION`。

5. **DNS 刚迁移时搜索引擎"抓不到 sitemap"**：NS 迁移后，全球 DNS 要 24–48 小时才完全生效。这段时间 Google/Bing 的爬虫可能还解析到旧 NS，于是显示"无法抓取"。这是时间差，不是配置错，会自动恢复。

6. **Cloudflare 代理（橙云）会隐藏 CNAME 目标**：给 Bing 加 CNAME 验证时，如果代理开成橙云，Cloudflare 返回自己的 IP，Bing 检测不到 `verify.bing.com` 就验证失败。解法：改成灰云（仅 DNS）。

---

## 结语

整个项目从"一个中文单语言站"变成"四语言、SEO 完善、已部署上线的内容站"，核心是搞懂了几件事：

1. **静态导出**让你不用管服务器
2. **Markdown 管线**让你发稿不改代码
3. **路径前缀 i18n**让多语言对搜索引擎友好
4. **hreflang/sitemap/JSON-LD**让搜索引擎正确理解你的站
5. **Cloudflare Pages + DNS**让构建部署自动化

理解了这些"为什么"，以后做任何网站都能举一反三。
